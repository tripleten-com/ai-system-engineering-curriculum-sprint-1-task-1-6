# Task 1.1 codebase guide

Use this guide when the project is new to you. You do not need to read every file before running
the system.

## Read these files first

1. `README.md` — setup, commands, scope, and operational limits.
2. `compose.yaml` — the running services and their startup order.
3. `src/domain/contracts.py` — data passed between the API, queue, worker, and database.
4. `src/ports/__init__.py` — the five provider-neutral interfaces.
5. `src/api/use_cases.py` — how a reading becomes durable queued work.
6. `src/worker/use_cases.py` — how queued work reaches a terminal state.
7. `src/adapters/` — how the ports reach PostgreSQL, Redis, and the deterministic model.
8. `tests/e2e/test_exception_workflow.py` — the externally visible workflow contract.

## Folder map

```text
task-1-1/
├── docs/                Student guidance, public contracts, and fidelity limits
├── src/
│   ├── api/             HTTP process and reading-acceptance workflow
│   ├── worker/          Background process and exception-processing workflow
│   ├── domain/          Shared state, data contracts, identity, and redaction
│   ├── ports/           Five provider-neutral interfaces
│   └── adapters/        PostgreSQL, Redis, model, logging, and tracing
├── infra/               Container, database, observability, and setup configuration
└── tests/
    ├── unit/            Isolated behavior
    ├── contract/        Interface and repository boundaries
    ├── smoke/           Running-platform readiness
    └── e2e/             External workflow behavior
```

The hidden `.devcontainer/`, `.github/`, and `.vscode/` folders support Codespaces, CI, and editor
tasks. Root files such as
`pyproject.toml`, `uv.lock`, and `compose.yaml` are standard project entrypoints.

## Runtime flow

```text
POST /api/v1/readings
        |
        v
src/api/routes.py
        |
        v
src/api/use_cases.py
   | redact and validate
   | derive exception identity
   | persist RECEIVED -> QUEUED
   v
src/adapters/queue/redis_streams.py
        |
        v
Redis Stream + consumer group
        |
        v
src/worker/runtime.py
        |
        v
src/worker/use_cases.py
   | persist PROCESSING
   | call ModelProvider
   | persist COMPLETED or FAILED
   v
GET /api/v1/exceptions/{exception_id}
```

The database state is authoritative. A queue acknowledgement happens only after the use case has
persisted a safe result.

## The five ports

| Port | Task 1.1 status | Responsibility |
|---|---|---|
| `ModelProvider` | Active | Produce the deterministic exception summary |
| `JobQueue` | Active | Publish, consume, recover, and acknowledge exception jobs |
| `Retriever` | Visible only | Define the future retrieval boundary |
| `ObjectStore` | Visible only | Define the future object-storage boundary |
| `SecretProvider` | Visible only | Define the future secret-reading boundary |

Ports belong in `src/ports/`. Provider details belong in `src/adapters/`. The domain does not
import either runtime process or any provider library.

## API and worker composition

`src/api/bootstrap.py` and `src/worker/bootstrap.py` are composition roots. They may choose
concrete adapters and own process startup or shutdown. They do not own business decisions.

Each process reads environment-backed settings through its own protected configuration module:

- `src/api/config.py`
- `src/worker/config.py`

Other source modules receive values or collaborators through function and constructor arguments.

## Test levels

| Level | Requires Compose | Main question |
|---|---:|---|
| Unit | No | Does one responsibility behave correctly, including failures? |
| Contract | Usually no | Do interfaces, schemas, paths, and dependency rules stay compatible? |
| Smoke | Yes | Did the complete local platform initialize and become observable? |
| E2E | Yes | Can an external client complete the API-to-worker workflow? |

Tests marked `runtime` require the running Compose stack. Fast authoring checks exclude that marker.

## Command path

```text
poe start
  -> build images
  -> start PostgreSQL and Redis
  -> run the initializer once
  -> start API and worker
  -> start local observability services

poe verify
  -> readiness
  -> smoke tests
  -> end-to-end workflow
  -> answer and protected-path checks
```

Use `poe stop` when you want to keep local data. Use `poe reset` when you need a clean run.

## Files without inline comments

Some formats must remain machine-owned or strict:

| File | Why comments are not added |
|---|---|
| `uv.lock` | Generated by uv; manual edits make the lock untrustworthy |
| `.python-version` | Contains one exact tool value |
| `.devcontainer/devcontainer.json` | Parsed as strict JSON by authoring checks |
| `.vscode/tasks.json` | Kept machine-readable and explained here |
| Grafana dashboard JSON | Provisioned directly by Grafana |
| E2E fixture JSON | Used as exact synthetic input |

The submission JSON Schema uses standard `$comment` and `description` fields because those are
valid JSON Schema keywords.

## Safe boundaries

Do not place secrets, personal data, solutions, held-out inputs, instructor assets, or protected
evaluator logic in this repository.

Task 1.1 changes are limited to `submission.yaml` and
`docs/student/task-1-1-baseline.md`. Read the remaining files to understand the system, but do not
change them for the Task submission.
